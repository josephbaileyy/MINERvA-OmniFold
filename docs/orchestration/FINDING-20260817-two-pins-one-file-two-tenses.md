# Two pins on one file are a defect only if both claim the same tense

**Row:** `BEN-406` (lane C, PET). **Date:** 2026-08-17.
**Instance raised and closed by the mediator; the tense rule and the search method are lane C's.**
**Not filed against `verify_hash_bindings.py`, which belongs to its owner with lane D's `1409/2` baseline.**

---

## 1. The apparent defect

Two pins of `nd-unfolding/pet/train_fullevent_nominal.py` disagree:

| site | value | kind |
|---|---|---|
| `sbatch_pet_fullevent_floor_replicate_array.sh:101`, `:117` | `91144bee…` | **precondition assertion** |
| untracked `STEP1_DYNAMICS` runtime receipt | `66aa1f8f…` | **runtime record** |

**It is not a disagreement.** The launcher's header states its own tense: *"a floor is only a floor under the
same code"* — **present tense about a future run**, a gate on what may execute. The receipt's structure
states its: `driver` / `driver_sha256` / `driver_output` / `driver_output_sha256`, i.e. *"this code ran and
produced this"* — **past tense**, a record of what did execute.

**Two claims about two moments. The rule that resolves it:**

> **Two pins on one file are a defect only if both claim the same tense.**

The false positive is generated by comparing a **historical record** against a **forward-looking guard** as
though they were two assertions about one state. Nothing to fix, nothing to reconcile.

## 2. The method rider, and it is worth as much as the result — `BEN-235` caught PROSPECTIVELY

Lane C's covering grep over the tracked tree found **all 7** `name`-then-`sha` pins of that file agreeing on
`91144bee…`, and **named its own blind spot before the answer arrived**: the pattern matches only the
*adjacency* form (`name … sha` on one line) and **would miss `path` and `digest` in separate JSON fields.**

**That is exactly the receipt's shape** — `driver` and `driver_sha256` are separate keys — **and the receipt
is untracked besides, one of the 721.** So the prediction was confirmed on both counts.

**The null was therefore reported as evidence about the search and ROUTED rather than recorded.**

> **A null whose blind spot you can name is a different object from a null you present as an answer.**

This is the first time on this campaign that `BEN-235`'s class was named *before* the disconfirming evidence
arrived rather than filed afterwards.

## 3. The gate already knows this class — which corrects the framing the observation arrived with

The observation reached me as *"a scope mismatch in the gate's own semantics."* **Read, it is narrower and
the gate is smarter than that.**

`docs/orchestration/verify_hash_bindings.py:370` is `if sha256(lp) == want:` — **current file content against
the pinned value.** So a runtime record *must* mismatch once its file legitimately changes. But `:78-80`
states the rationale verbatim:

> *"Bindings known to have drifted before 2026-07-28 and deliberately not 'fixed': **these receipts record
> what ran at submit time, and rewriting their hashes would falsify history.** Listed so real regressions
> stay visible above the noise."*

**So the gate is not semantically confused. It has the concept, it has an exemption channel
(`KNOWN_PREEXISTING`), and the channel is scoped to drift *before 2026-07-28* — while the repo has no end
date.**

**Consequence:** every legitimate post-cutoff change to a pinned file produces a mismatch of **the same
species** as those four entries, with **nowhere to be recorded**. That is a limit on the exemption list's
scope, not a defect in the comparison.

**The remedy is additive provenance rather than a repin: bind the historical bytes to the IMMUTABLE COMMIT
that carried them, not to the live path.** This is the pattern lane C already used when it declined to
extend `KNOWN_PREEXISTING` for exactly this cutoff reason — a repin would make a receipt assert that a file
which did not produce an artifact did produce it.

> **CONSEQUENCE FOR TRIAGE, and it is the operational half: a binding mismatch is not automatically a thing
> to FIX. One may be a receipt doing its job.** Anyone treating a mismatch count as a defect count should
> first ask which tense each side claims.

## 4. The rule constrains NEW verifiers, not only old ones

> **A check must compare like tense to like.** Assert either **present** (tree vs tree) or **past
> self-contained** (a receipt asserting agreement between two things *it* recorded at one moment).
> **Never present-vs-historical without an exemption channel that has no expiry.**

**Applied immediately:** `C_stat^data`'s verdict path may contain **no cross-tense comparison**
(`RULING-20260817-lanec-data-only-cstat-is-a-second-product.md` §5). A present-vs-historical check there
would decay to `FAIL` the moment a pinned file legitimately changes, **and it would inherit an escape hatch
that expired on 2026-07-28.** A new product must not be built on that.

## 5. What is not claimed
