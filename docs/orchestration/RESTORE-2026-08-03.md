## Step 2 — Resolve the Gate-2 units question, then re-issue *both* freezes

`gate2_target_runtime.py:421-422` divides the input muon scalars by 1000.0 on the
way into the canonical FPS grid. Whether that is correct depends on the units the
real dump actually carries, and the failure is asymmetric:

- If the dump is in **MeV**, the division is right and everything is consistent.
- If the dump is already in **GeV**, the division misscales *both* histograms
  identically. The domain guard at `gate2_target_runtime.py:432-435` still passes,
  and `rel_l1` / `max_rel` / `cosine` then compare two identically-wrong
  histograms and agree. **The gate passes while being wrong.**

This was settled empirically on known-unit inputs (2026-07-26, run log): dividing
GeV scalars by 1000 retains 500/500 rows inside the canonical grid and passes
silently; the pass-through patch on MeV input retains 0/500 and dies loudly.
So the procedure is unambiguous — **run it against the real dump and read the
retained inventory**:

1. Inspect `measured_scalars` in the real dump directly (min/max/median of the pT
   and p∥ columns). Muon p∥ up to 120 GeV vs 120000 MeV is not a subtle
   distinction; this alone answers it.
2. Cross-check by running the domain guard both ways. Pass-through retaining 0
   rows ⇒ input is MeV ⇒ keep the `/1000.0`. Both retaining everything ⇒ trust
   step 1, not the gate.

**Then re-issue the freeze — both halves of it.** The Gate-2 canonical runtime
receipt `nd-unfolding/g2_fullevent/gate2/final/G2_GATE2_TARGET_RUNTIME_RECEIPT.json`
(verdict `GATE2_CANONICAL_RUNTIME_PASS_INDEPENDENT_PROMOTION_PENDING`) binds
**two** code files at once:

| role | path | frozen sha256 |
|---|---|---|
| validator | `nd-unfolding/pet/gate2_target_runtime.py` | `a8539d83…f8a51ee` |
| loader | `nd-unfolding/pet/fullevent_fps_dataloader.py` | `c0521d21…6d0fdd5` |

Editing the validator therefore voids the loader's binding too, even if the
loader is untouched, because the receipt that froze it is no longer the receipt
that passed. Any units patch means **deliberately re-running Gate-2 and
re-issuing the receipt** — never hand-editing a hash. Re-run Step 0 afterwards.

If the answer is "MeV, no change needed", nothing needs re-issuing. Record the
finding anyway; the point is that the question is closed with evidence.

## Step 7 — Real-data arm of the event-feature ranking (B-3 evidence)

Added 2026-07-30. The closure arms ran on Delta that day (`feature_rank_arms.py`, job
20599606) and delivered the matched positive control, the retraining floor, and the A-vs-B
sampling floor. What they could **not** do is compare feature blocks on real data: the xps2 pc

— all searched 2026-07-30, not assumed. It lives on `/pscratch`.

**Why this is worth a restore step.** B-3 says the contract's `pet-fullevent-fps-v1` label
(full muon object + vertex + view/timing) overstates the estimator that was actually validated
on `{pT, p‖}`. Extending the feature block to match the label needs new C++ branches plus an
FPS-CV regeneration (G2), and today nothing measures whether that buys anything.
`FULL_EVENT_FEATURE_CONTRACT.md:116-123` justifies the reduction by assertion, and the one
quantitative comparison (CLM-006) mixes niter, train size, and representation in a single
number with no tolerance. `eavail`/`q3` are the cheap proxy: already dumped on **both** legs
(`SCALAR_COLS`), unread by the adopted schema, and requiring no dump or bound-file edit. If two
free features move nothing above the floor, that is evidence the event-feature channel is
saturated and the expensive extension is unjustified. If they move it, the channel has headroom
and the C++ ask has empirical support.

**First action is a verification, not a run.** The sidecar's `measured` array is recorded as
`(4116128, 5)` (`HANDOFF_fps_step3/fps_pipeline_state.md:511`) on the 5D axis order
`(pt, pz, eavail, q3, W)` (`project_cov_nd.py:13`), which would line up with
`SCALAR_COLS = {"pt":0,"pparallel":1,"eavail":2,"q3":3}`. That alignment is inferred from two
documents, never executed. Confirm it against the file before trusting any arm:

```bash
python3 -c "
import numpy as np; d=np.load('of_inputs_5d_fps_xps2.npz',allow_pickle=True)
m=d['measured']; print(m.shape, m.dtype)
print('col medians', np.median(m,axis=0))   # expect pT ~O(1) GeV, p|| ~O(3-5), NOT -9999
"
```

If `measured` turns out to be 2-column, or the order differs, the real-data arm is blocked on a
re-dump and should be recorded as such rather than run on a guessed column map — a silent
mis-map would put `q3` where the classifier expects `p‖` and produce a confident wrong answer.

Then run the same driver with the data leg wired in, at the identical config the closure used
(`niter 2 / epochs 8`, matched rows/split/seeds) so the closure floor transfers:

```bash
python3 pet/feature_rank_arms.py --cache <real-data cache> --arms base,eavail,q3,both
```

**Read it against the floor, not against zero.** The decision rule is the one the closure
established: an arm counts only if its shift clears the base seed-to-seed spread *and* its net
uncertainty change in that direction is non-positive. A feature that moves the central value
while inflating `C_ML` more than it shrinks `C_stat` is a net loss, and the seed policy
(`FULL_EVENT_FEATURE_CONTRACT.md:37-39`) already separates those two.

**Out of scope here.** This ranks features that EXIST. The eight genuinely-absent extension
arrays (`reco_muon`, `reco_vertex`, `reco_view`, `reco_time` and their four `data_*` twins —
referenced **zero** times by the loader, verified 2026-07-30) cannot be ranked until G2 lands.
For those, the only pre-G2 evidence is a synthetic unread-variable closure, and note the
asymmetry that makes muon `φ` the better probe than view/timing: view and timing are
detector-only, so a tilt in them is recoverable at step 1 but has no truth counterpart, and
letting step 1 absorb what may be a *simulation* error propagates a fake shift into truth.
"Can see it" is not "should see it" for reco-only features.

### Step 7b — Measure `corr(cos φ, pT)`, the one number the coupled-φ sweep needs

Added 2026-07-31, after Delta jobs 20636012/13 and 20648055/56 (10 couplings × 2 seeds).

**What the sweep established.** The extension arm recovers an azimuthal mismatch at a flat
**+0.8986 ± 0.0157** across the whole tested range, corr(cos φ, pT) = 0 → 0.898. It does not
degrade with coupling at all. What erodes the extension's *marginal* value is only the baseline
becoming less blind: the gain falls through the +0.25 clearance at
**corr = +0.777, band [+0.764, +0.794]**. So one real-data number decides whether the φ channel
is worth anything: how correlated muon azimuth actually is with the muon block.

**φ is NOT in the npz — verified, don't assume otherwise.** `of_inputs_pc_fps_xps2.npz` (9.03 GB)
carries exactly 18 keys: `data_pot`, `edges_0..3`, `gen_feats`, `measured_pc`,
`measured_weights`, `num_part`, `part_gen`, `part_reco`, `pass_reco`, `pass_truth`, `reco_feats`,
`reco_scalars`, `truth_scalars`, `w_reco`, `w_truth`. No `reco_muon`, no `data_*` twin. The
extension arrays are **absent from the dump**, not merely unread by the loader — those are
different claims and only the stronger one is true.

**But the measurement is still cheap and pre-G2.** `mu_reco_phi` is an existing branch in the
source ntuples — `dump_pointcloud_inputs.py:74` already names it in `RECO_MUON_BRANCHES`. So this
needs a small ROOT read of two branches (`mu_reco_phi` and the pT scalar: `measured` for data,
`sim` for MC signal reco), with no cloud, no event loop, and no FPS-CV regeneration. It is not a
numpy one-liner on the npz, and it is not the G2 dump either. Do it on the reco leg — the leak is
about what the reduced schema reads at reco level.

**Decision rule.** Below corr ≈ 0.78 the extension's φ channel buys measurable capability; above
it, it does not. Expect to land far below: corr 0.777 required 7.8% acceptance in a synthetic
thinning built to maximize the coupling, and at corr 0.30 — already generous for a real
acceptance effect — the gain is still +0.82. The likely outcome is a comfortable pass with ~3× of
margin, and the point of measuring is to say so with a number instead of an assumption.

**Do not use `leak = corr²` to shortcut this.** That relation held to 0.004 over corr ≤ 0.62 and
was **falsified out of sample** (residuals +0.047 and +0.052 against a 0.0233 tolerance at corr
0.79 and 0.85). Pearson corr² captures only the linear share of the dependence; strong coupling
adds nonlinear structure a classifier exploits. It is a *lower bound* on the leak, so it errs by
**overstating** the extension's value — fine as a weak-coupling sanity check, wrong as a
substitute for reading the measured curve in `products/pet/coupled_phi_curve.json`.

**What this still is not.** A closure. The crossing is a property of a synthetic acceptance
thinning, so it bounds the coupling axis; it says nothing about whether real data carries an
azimuthal mismatch at all. Recovering the tilt through a pT proxy is also not the same as seeing
φ — at corr 0.62 the baseline "recovers" 0.389 of the tilt for the wrong reason, and would keep
doing so when the true correlation shifted.
