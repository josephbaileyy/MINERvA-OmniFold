## 1. Sums gate — CLOSED

The expected counts are 6, 12, and 36.

`inputs/sbatch_t3p.sh:128` writes each job's `SHA256SUMS` as `find runs -type f -name '*.npz' | xargs sha256sum`, so the file lists every `.npz` under `runs/` at that moment, one GNU `sha256sum` line per file. The write sits after the task queue and before `pair` (`:134`, which writes `pair.json`) and `DONE` (`:137`). The connect accepts a job only when `log-<job>/DONE` is non-empty and `STOP` and `FAILED` are absent (`t3p_read_connect.sh:68`), so the sums it checks are from jobs that finished the queue.

`inputs/t3p_submit.sh:147-149` requires the queues to be dry 6, q3 6, floor 24. Dry ran first, then q3, then floor, and each job leaves its products in `runs/`. The cumulative tree is therefore 6, then 12, then 36 files, and the three sums files have that many lines. The stand-in, built at M_V1, shows the same split: `DONE` records tasks 6, 6, and 24, `wc -l` prints 6, 12, and 36, and `find` prints 36 npz (`inputs/standin-ok.log.txt:2-6` and `:19-21`). Paths are `runs/<arm>/<truth>/t3p_<arm>_<truth>_s<seed>.npz` (the stale-sums failure names `runs/B0/A7_gibuu/t3p_B0_A7_gibuu_s991000.npz`). Those lines match the gate regex.

The gate is `t3p_read_connect.sh:109-116`:

- `nl=$(grep -c '' "$SUMS")` is the line count, including a last line with no newline.
- `ng=$(grep -cE '^[0-9a-f]{64}  runs/[^[:space:]]+\.npz$')` counts only a 64-digit lowercase hash, two spaces, and a `runs/…npz` path.
- Both must equal the per-job want (`dry:6 q3:12 floor:36`).
- Then `( cd "$OUT" && sha256sum --strict --quiet -c "log-$j/SHA256SUMS" )` must succeed.
- `runs/` must contain exactly 36 `.npz` files (`:118-120`).

There is no `set -e` (`:31`, `:33` is only `pipefail`). `grep -c` exits 1 when the count is 0; the assignment still stores 0 and the numeric test runs. An empty file cannot pass.

A malformed, empty, or truncated sums file fails this gate:

- Empty: `nl=0`, `ng=0`. `inputs/standin-empty_sums.log.txt:31-32` stops with `STOP: log-dry/SHA256SUMS is not 6 well-formed lines` before `sha256sum -c`.
- One byte deleted from a hash: the line is no longer 64 hex digits, so `ng` drops. `inputs/standin-deleted_byte.log.txt:33-34` is `12 lines, 11 well-formed` and the same STOP. The same regex on a 63-hex line under the local BSD `grep` gave `nl=1 ng=0`.
- A comment, a blank line, or any other non-matching line makes `nl > ng`. A local mixed file (one good line plus a comment) was `nl=2 ng=1`.
- A truncation that cuts a line in half leaves a last line the regex rejects (`nl=1 ng=0` on a 40-byte prefix). Dropping whole lines makes `nl` smaller than the want. The job's file has exactly the wanted number of lines, so either kind of truncation misses `nl == ng == want`.
- A well-formed line whose hash is wrong still has `nl == ng == want`, and `sha256sum --strict -c` rejects it. `inputs/standin-stale_sums.log.txt:35-38` is 36/36 well-formed, then `FAILED` and `STOP: the products are not log-floor/SHA256SUMS's`, before the read.

The only truncation that keeps `nl == ng == want` is removing the final newline and nothing else. `grep` still counts that last line (local: 3 lines with no final newline, `grep -c` 3, `wc -l` 2). `sha256sum -c` reads it with `getline` and checks the same hashes. No checksum is missing or altered.

`sha256sum -c` checks the listed files. It does not care that the paths are unique. A file of N copies of one valid line would meet the count and `-c` while leaving other products unchecked. That file is well formed. Empty, short, mixed, and truncated inputs do not produce it, and the job's `sha256sum` writes one line per file present. The rev 0 hole (an empty or unparsable file passing `-c`) is closed by the count plus the regex, with `--strict` behind them.

`grep -c` at `:112` is not a pipeline. On an empty file it exits 1 and prints 0. With no `-e`, the script continues, prints `0 lines, 0 well-formed`, and stops on the numeric test (`standin-empty_sums.log.txt:31-32`). A real sums file has matches, so `grep` exits 0. A local assignment of `grep -c ''` on an empty file returned status 1, stored 0, and the next command ran.

`head` closing a pipe can make the writer exit 141. A local `yes COMPLETED | head -1` under `pipefail` returned 141 and still captured `COMPLETED`; the following command ran, and `[ "$st" = COMPLETED ]` passed. Lines 69 and 84 do not check that status, so a 141 does not BAIL. The state test BAILs only when the captured string is not `COMPLETED`. The seven variants that got past the pre-log job check all did so with `pipefail` on.

No checked pipeline has a left side that exits nonzero on a legitimate success. `git status` exits 0 when the tree is clean. `wc` and `sort` read their whole input. `dd`, `sha256sum`, and `cut` in the copy loop do the same. `find` exits nonzero when a root is missing or unreadable, and that stop is the check added in rev 1.
