You are an independent reviewer of a small, high-stakes data-writer for a physics release. Read only; change nothing.

WHAT IT IS. EVW5D reruns ONE existing unfold (MINERvA 5D OmniFold, "configuration (e)", the sixteen-cell result's
central value) through its pinned driver, unchanged, and saves the per-event unfolded weights so they can be published
as the unbinned central value. A previous run of the same unfold (the "ESS run") reproduced the published product's
xsec_flat byte for byte, so the rerun is expected to be exact. The new code adds the save, a read-back, controls, a
done marker and an acceptance check.

FILES (all in this directory):

- evw5d/evw5d.py              -- the writer

SCOPE RULE (the director's): a finding BLOCKS only if it could change the published weights, the published constants,
or what a gate accepts (i.e. a wrong or unverified weight/constant/key could be published, or a gate could pass when
it should fail, or fail when it should pass on the real run). Everything else is NON-BLOCKING; list it briefly.

QUESTIONS TO ANSWER, with file:line evidence:
1. Key and alignment: is (npz sha256, entry = index of the row in MCgen among pass_truth rows, in order) correct for
   the rows whose weights the driver histograms? Can rows be reordered/filtered between the npz and the unfold on the
   central pair (--pairs=-:-, construction data)? Does C-KEY really prove alignment?
2. Weights: is w_unfolded exactly the driver's histogram weight (s5c_unfold.py:138)? Is wpush the right element of
   omnifold_loop's return value? Any dtype trap (float32 MCgen, float32/float64 wpush, bool masks)?
3. Gates: C-BIND (byte-equal xsec_flat + meta minus per-run fields) and C-F (f to 1e-14 vs the data product, from the
   result and from per-row contributions). Could either pass wrongly or fail spuriously on the real run (e.g. summation
   order, the meta comparison, the contributions formula vs the driver's extraction xsec_nd.py)?
4. Read-back: do C-FILE / C-SELF / C-FLOW check the saved bytes independently of the in-memory table (the file is
   hashed and parsed from the same bytes)? Any product written but not checked? Any constant a user needs to
   reproduce the result or rebin that is missing or wrong (flux by pT bin, POT, N, 1e4, completeness, volume, map,
   edges)? Is the formula in constants.json right?
5. Binning independence (section 4): is the claim that the training sees no interior bin edge correct for this driver
   path? Does the C-COL test prove what it says? Is the stated limit (completeness only binned on the fine grid) right?
6. Completeness (C-COMPLETE) as a measurement: is it computed correctly, and is reporting it as a finding (not a gate)
   safe for the published weights?
7. Acceptance / done marker / accepted(): can a consumer be fooled into accepting a partial or altered product?
8. The job script and read discipline: anything that could make the real run read the wrong input or write outside
   its output root?
9. Tests and mutants: any gate or check line that no test can make fail (a surviving or missing mutant that matters
   under the scope rule)?

OUTPUT: start with one line "VERDICT: GO" or "VERDICT: GO WITH CHANGES" or "VERDICT: NO-GO". Then numbered findings,
each tagged BLOCKING or NON-BLOCKING, each with file:line, the concrete failure scenario, and a suggested fix. Be
concrete; do not pad. If you checked something and it is fine, say so in one line under "Checked and fine".
