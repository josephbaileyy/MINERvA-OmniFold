## (b) Findings

**F1 — MINOR — the claim "bin edges" is wider than what the test compares.** At `2d-unfolding/tests/test_selective_io.py:592`, `output_objects()` records only the **X-axis** low edges (`obj.GetXaxis().GetBinLowEdge(i)`) for every TH1/TH2. Y-axis (p_||) edges, entries and stats are not compared in the CLI tests. Even so, REPORT §6 (CommandLine row) says "each histogram's contents, errors and bin edges", and the task asked for "bin maps".
- Scenario: a change to the p_|| binning of an output TH2 that leaves the flattened cell contents equal would pass. This is unlikely, because the edges are module constants shared by both settings. The gap is in the claim, not in the behaviour.
- Smallest fix: add `GetYaxis()` edges (and optionally `GetEntries()`) to `output_objects()`. Or narrow §6 to "contents, errors (flow included) and X-axis edges".

**F2 — MINOR — the caller table in REPORT §8 does not cover its stated population.** §8 states its population as "`git grep` at the base for the driver's name and its four loaders … then each hit opened". The table lists the 3D driver, `xsec_3d.py`, `gen_to_xsec5d.py`, `redraw_central_only.py`, `build_1d_ibu_inputs.py`, N2 and the tests. My rerun found many more importers that the table does not mention:
- `git grep -n "import unfold_2d_omnifold_unbinned"` at `6486867f` finds **about 45 more**, among them `nd-unfolding/unfold_nd_omnifold_unbinned.py:78`, `pet_systematics*.py`, `sweep_bank*.py`, `s5c_with_estimator.py:98` (which monkeypatches `u2d.refine_stay_positive` and `_make_bkg_classifier`), `pet/*`, `unified_throw*.py` and `2d-unfolding/plot_2d_cross_section.py:297`.
- None of them is affected. The new module-level code is three stdlib imports plus definitions, with no import-time ROOT call (`_branch_address_api()` is lazy). No caller uses `import *`. `git grep 3cc5adc7` outside `docs/orchestration/state` finds only the new reference subsection. Only N2 calls one of the four loaders directly.
- The defect is a covering claim that is not met, not a broken caller.
- Smallest fix: add a row such as "~45 `nd-unfolding`/`pet`/plot importers: constants, helpers, `refine_stay_positive`; unaffected (no import-time change)".

**F3 — MINOR — the §1 headline omits the stub.** REPORT §1 bullets 2–3 say the CLI path gives "the same OmniFold inputs, estimator arguments and outputs" and that the default's "OmniFold inputs and outputs equal those of the pre-change driver". These outputs come from a **stub** helper with deterministic weights; nothing was trained. §6 and §11 say so, but a reader of §1 alone would take "outputs" as trained outputs. The reference subsection's "every output histogram and metadata object" has the same problem.
- Smallest fix: insert "(stub helper; no training)" in those two §1 bullets and in the reference sentence.

**F4 — NOTE — small record inaccuracies.**
- REPORT §3 places the rooted insert "at `:2059`". `:2059` is the `_OF_PY =` literal; `sys.path.insert(0, _OF_PY)` is at `:2061`, still inside `main()` (base: `:1722`).

- The reference subsection says "the guard refused LightGBM's `lscpu` probe". The probe is loky's, reached through LightGBM/joblib, as `Q/sb1-run/REPORT.md` §7.6 and REPORT §9 say.

**F5 — NOTE — in the tests, address restore is detected only by a crash.** I mutated `call_loader` to drop `restore_branch_addresses(tree, addresses)` (mutant M6, applied to a scratch copy). The `Loaders`+`Refusals` run then died with `*** Break *** segmentation violation` in `array_new`, inside the reused-tree path.
- So the restore is necessary, and its absence is detected, but by heap corruption rather than an assertion. Inferred: crash timing could vary by platform.
- Optional: add an assertion that after a derived call the derived branches' addresses equal the pre-call snapshot (null on a fresh tree). My probe C below shows this holds.

**F6 — NOTE — portability of the routing script and the helper scripts.**
- `S/checks/frozen_package_checks.sh` is safe:
  - it never runs `git config`;
  - it writes only `.git/worktrees/` through `worktree add`/`remove`;
  - it runs the suites inside the throwaway worktree;
  - its byte check uses committed `HEAD`;
  - an `EXIT` trap removes the worktree. The worktree count was 38 before and after each of my two runs.
- Two nits:
  - XR's `manifest --check` uses bare `python3`, not `$py`. Inferred: this matters only if `python3` on the integration host is too old.
  - An unreachable commit (for example in a shallow clone) makes `git diff` fail, which is reported as "differs from its frozen commit" with exit 2. That is fail-closed, but the message is misleading.
- `frozen_all.sh`, `run_frozen.sh` and `run_suites.sh` hard-code the owner's scratchpad and canonical-checkout paths. They are records of what ran, not reusable tools. Only `frozen_package_checks.sh` is proposed for routing, and it is portable.

**F7 — NOTE — design.** `expected_loader_branches` deliberately restates the four loaders' selection logic: the lateral-fallback and `use_weights` conditions. Branch names come from the shared helpers. The two copies are kept consistent fail-closed: a mismatch refuses before any read. The consequence is that any future loader edit must update the rule, or `--branch-select derived` refuses. This is disclosed in §11 and acceptable.
