## New findings

1. **SHOULD-FIX: `cleanup` can refuse every run on the cluster (`evw2d.py:676-679,1053`).** `identity()` includes `st_dev`. The run records it on a compute node. Cleanup likely runs on a login node, because it needs the ROOT environment. On network filesystems such as Lustre, `st_dev` is a per-mount anonymous device number, so it can differ between nodes. If so, `cleanup` raises "not the file the accepted run verified" and the staged copies stay. It fails closed, but cleanup would never work.
   - Fix: compare `ino`, `size`, `mtime_ns` and `mode` in `cleanup`. Keep `dev` for the same-node C-STAGE check.
   - Test: run `cleanup` from a login shell after a compute-node run at the binding.

2. **SHOULD-FIX: `references.npz` is hashed and then read again (`:591-594`).** This is the same two-read pattern the config had. The references feed C-EXACT-ER and C-EXACT-PAPER. Only a race exploits it, so it is out of scope for BLOCKING.
   - Fix: read the bytes once, hash them, and pass `io.BytesIO(raw)` to `np.load`.

3. **NOTE: the allocation gate only accepts what is numeric (`:249-251`).** Slurm's reserved step IDs (`0xfffffffa`–`0xfffffffd`, covering interactive, batch, extern and pending) are numeric strings. If a batch shell exports one as `SLURM_STEP_ID`, `isdigit()` passes it. Add `int(step) < 0xfffffff0`. At the binding, print `SLURM_STEP_ID` in a plain sbatch shell and in an `srun` step.

4. **MINOR: `cleanup`'s ledger uses `O_NOFOLLOW`, which does not stop a hard link (`:1058`).** A hard link named `deletions.tsv` to a pinned file would still be appended to. Add an `st_nlink == 1` check on the opened fd. Out of scope as a mistake.

5. **NOTE: §8's named residual is accurate but incomplete (declaration `:342-346`).**
   - The driver also opens the flux and MC file by name. A swap there that changes the flux moves σ, which is the exactness gates' case.

   - A swapped omnifile that changes only the data POT scales `w_prior`, `w_unfolded` and the `data_pot` constant together. σ ∝ pot_scale / data_pot = 1/mc_pot stays the same, so the exactness gates would not see it. This holds if the fit is insensitive to the overall MC-to-data scale. That is not tested, so I can't say it holds.
   - Only a hostile same-account process can do this, so it is out of scope.
   - The same class also covers a pinned source swapped and restored around the import. The general sentence covers it, but "one residual is named" understates the class.
   - Fix: reword §8 to say the driver opens all its inputs and its source files by name. Optionally add one cheap check that `get_pot_scales`'s output equals a POT read from the held file.
